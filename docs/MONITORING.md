# 本番環境監視・運用ガイド

## 小学コレ！道徳 - リリース後の監視と運用

**対象**: v1.0.0+ の本番環境

---

## 概要

本ドキュメントは、小学コレ！道徳アプリの本番リリース後の監視・運用手順を定めています。

### 監視の目的

```
✅ ユーザーへの影響を最小化
✅ パフォーマンス・信頼性を維持
✅ セキュリティ脆弱性を早期発見
✅ ユーザー満足度を向上
✅ データドリブンな改善を実現
```

---

## 監視対象と KPI

### 1. **アプリ安定性**

| KPI | 目標値 | アラート閾値 |
|-----|-------|-----------|
| クラッシュレート | < 0.5% | > 1% (P1) |
| ANR（反応なし） | < 0.1% | > 0.5% (P2) |
| 起動時間 | < 3秒 | > 5秒 (P2) |

### 2. **パフォーマンス**

| KPI | 目標値 | アラート閾値 |
|-----|-------|-----------|
| API 応答時間 | < 500ms | > 1000ms (P2) |
| フレームレート | 60 FPS | < 50 FPS (P3) |
| メモリ使用量 | < 150MB | > 200MB (P3) |

### 3. **ユーザー体験**

| KPI | 目標値 | アラート閾値 |
|-----|-------|-----------|
| 日次 Active Users (DAU) | - | 20% 以上の低下 (P2) |
| セッション継続時間 | > 5分 | < 3分 (P3) |
| ユーザーリテンション（Day 1） | > 30% | < 20% (P2) |
| App Store レイティング | 4.0+ | < 3.5 (P3) |

### 4. **セキュリティ**

| KPI | 目標値 | アラート閾値 |
|-----|-------|-----------|
| セキュリティ脆弱性 | 0 件 | 1 件以上で即対応 (P1) |
| 認証エラー | < 0.1% | > 0.5% (P2) |
| データ流出 | 0 件 | 検知時即対応 (P1) |

## アラート設定

### 🔔 Firebase Alerts

**設定画面**: Firebase Console → Performance Monitoring → Alerts

```
【Threshold-based Alerts】

1. クラッシュレート
   - 閾値: > 1%
   - 通知先: #incidents Slack
   - 優先度: P1

2. ANR（Application Not Responding）
   - 閾値: > 0.5%
   - 通知先: #incidents Slack
   - 優先度: P2

3. 起動時間
   - 閾値: > 5秒（中央値）
   - 通知先: #monitoring Slack
   - 優先度: P2

4. API レイテンシ
   - 閾値: > 1秒（95パーセンタイル）
   - 通知先: #monitoring Slack
   - 優先度: P3
```

### 🚨 Sentry Alerts

**設定画面**: Sentry → Alerts

```
【Alert Rules】

1. 新しいクラッシュ
   - 通知先: #incidents Slack
   - 優先度: P1
   - メッセージ: "@channel New critical error"

2. エラーレート上昇
   - 条件: 前時間比 > 100% 上昇
   - 通知先: #incidents Slack
   - 優先度: P2

3. リグレッション検知
   - 条件: 前バージョンで解決済みエラーが再発
   - 通知先: #incidents Slack
   - 優先度: P2
```

### 📊 Google Play Console Alerts

**設定画面**: Google Play Console → ポリシー → アラート設定

```
【通知】

1. クラッシュ率の急上昇
```

## インシデント対応フロー

### アラート受け取り

```
1. Slack アラート受け取り
   → #incidents チャネルに自動投稿

2. インシデント評価（5分以内）
   - 問題の重大性
   - 影響を受けたユーザー数
   - 対応の優先度（P1/P2/P3）

3. 対応チーム招集
   - インシデント主導者を割り当て
   - Google Meet での会議開始
```

### インシデント調査

```
1. 問題の特定（15分以内）
   - エラースタックトレース確認
   - 再現性確認
   - 影響範囲の特定

2. 根本原因分析
   - Firebase ログを確認
   - コード変更履歴を確認
   - 外部サービスに問題がないか確認

3. 修正方針の検討
   - ホットフィックスが必要か
   - ユーザー通知が必要か
   - ロールバックが必要か
```

### インシデント対応

```
1. 緊急対応（P1）
   - リアルタイム修正・リリース
   - 対応時間: 3時間以内

2. 高優先度対応（P2）
   - 翌営業日中に対応
   - 対応時間: 24時間以内

3. 通常対応（P3）
   - バッチリリースに含める
   - 対応時間: 1週間以内
```

### インシデント終了

```
1. 修正確認
   - ストアで修正バージョンが配信されているか確認
   - クラッシュレートが低下したか確認

2. ユーザー通知
   - 重大な問題の場合、メール通知
   - Twitterなどで告知

3. ポストモーテム（Post-mortem）
   - 問題の振り返り会議
   - 根本原因と対応策
   - 再発防止策の検討
```

## パフォーマンス最適化

### 📊 パフォーマンスプロファイリング

定期的にアプリのパフォーマンスをプロファイリング：

```bash
# Android でのプロファイリング
flutter run --profile

# または CPU Profiler を使用
# Android Studio → Profiler → CPU

# iOS でのプロファイリング
flutter run --profile -i

# Xcode → Instruments で詳細分析
```

### 🎯 パフォーマンス改善の優先度

```
P1: アプリ起動時間 > 3秒
P2: 画面遷移 > 1秒
P3: UI フリーズ（16.67ms 以上）
P4: メモリリーク（使用量が増加し続ける）
```

## セキュリティ監視

### 🔐 セキュリティ脆弱性監視

```bash
# 依存関係の脆弱性をチェック
pub outdated

# セキュリティスキャンを実行
flutter analyze --no-pub

# Bandit（Python）で BackEnd を検査
bandit -r backend/
```

### 🛡️ データセキュリティ監視

```
【監視項目】
1. Firebase Firestore ルール
   - 不正なアクセスパターン
   - ルール変更の履歴

2. Firebase Storage
   - 予期しないファイルアクセス
   - 異常なダウンロード量

3. 認証
   - 不正なログイン試行
   - トークン悪用
```

### 📋 セキュリティ監査

```
【定期監査スケジュール】
- 毎月: OWASP Top 10 チェック
- 四半期: 外部セキュリティ企業による監査
- 年 1 回: ペネトレーションテスト（侵入テスト）
```
